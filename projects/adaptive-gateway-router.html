Adaptive payment-gateway router

A router that notices when a payment gateway starts failing and moves traffic to healthier ones on its own, learning from each transaction's outcome.

Razorpay · 2026 · Owner: framing, simulator, agent, benchmark, shadow-mode and rollout measurement; platform engineering owned production integration

Industry project at a payments company. Code and data are proprietary; this is a methods write-up. All figures are from the synthetic benchmark.

Problem

A payments platform routes each transaction to one of several gateways. Gateways degrade suddenly, partially and temporarily, and static routing rules keep sending traffic to a degraded gateway until someone notices and re-weights by hand. Detection is measured in hours, and every hour of mis-routed traffic is failed payments and lost revenue. Incidents of this shape motivated the project.

Rejected: predict

Forecast each gateway's success rate and route to the best forecast. Fails exactly when it matters: gateway failures are non-stationary, rare in training data, and by the time a forecast updates the damage is done.

Chosen: respond

An agent that observes only the outcomes of transactions it routes — success, failure, latency — and shifts traffic away from a gateway the moment its observed health drops. No forecasting; the skill being learned is adaptation.

Key insight Gateway failures are close to unpredictable, but reacting to them fast is tractable. Framed as a non-stationary multi-armed bandit (a sequential decision problem where each choice reveals only its own outcome, and the best choice changes over time) — explore enough to notice a gateway has recovered, exploit enough not to waste transactions on one that hasn't — the problem stops needing a model of the future.

Observations, actions, environment

Constraint
The router never sees a gateway's true state. Everything it knows is inferred from transactions it sent — the same constraint production has.
Action
Choose one of N gateways for each transaction.
Observation
A small set of per-gateway features, each derived from a rolling window of that gateway's recent outcomes; neutral defaults until a gateway has been sampled a few times.
Reward
The signal the agent optimises: success rewarded, failure penalised (less than success is rewarded, so the agent keeps trying), latency penalised linearly, and a bonus for switching away from a gateway whose success-rate trend has turned down — rewarding proactive switching before failures accumulate.

Simulator. Each gateway carries hidden parameters the agent never sees — a base success rate, volatility, current health, and a degradation pattern drawn from {stable, slow-decay, sudden-crash, bursty}. A turbulence manager randomly starts degradations, walks the success rate down gradually to a severely degraded floor, holds it there for a while, then recovers it slowly; latency spikes occur independently. Gradual degradation and slow recovery were deliberate: sudden crashes are easy to detect, slow decay looks like noise. The environment was made more turbulent than production, so a router that copes here has margin.

Production features. The same 8 observations are computed live from rolling windows of recent outcomes, per gateway, and served to the router.

Approach

  1. Score every gateway with an upper confidence bound (UCB)

    UCB = empirical success rate + exploration bonus + staleness bonus − latency penalty. The exploration bonus is the UCB1 algorithm's √(log N / nᵢ) — large for gateways sampled rarely, shrinking as evidence accumulates. A staleness bonus lifts any gateway that hasn't been sampled for a while, so a recovered gateway gets re-tried. Slow gateways are penalised.

  2. Detect drift and explore harder

    Before each decision, compare the current gateway's success over its most recent transactions with the batch before. A sharp drop flags degradation and temporarily raises the exploration rate to find alternatives. Otherwise exploration decays over time toward a small floor that never reaches zero — the router keeps checking.

  3. Never do the obviously wrong thing

    A hard floor: no traffic to a gateway whose observed success rate is below a threshold. A general safety check, cheap in the benchmark, and the kind of guarantee a payments team needs before trusting a learning system.

  4. Learn online, not offline

    No retraining step. The tracker is the model; every transaction updates it. Gateway behaviour changes faster than any offline model could be refreshed.

  5. A PPO policy, trained but not in the loop

    A Proximal Policy Optimization (PPO) agent — a standard deep reinforcement-learning algorithm — with a small neural-network policy was pre-trained in a Gymnasium environment on the simulator, with the reward above, as a candidate prior for the online layer. The benchmarked and deployed router makes its decisions from the observation tracker alone; the PPO policy is not in the decision path. It's kept as the natural next experiment (see below).

Benchmark

Two routers under the same observation-only constraint, in the turbulence simulator, at three scales. The rule-based router stands in for conventional threshold-based routing: stay on a gateway until its observed success rate over a short window falls below a fixed threshold, then switch, with a cooldown. All figures below are from the synthetic environment and are reported relative to that baseline.

The 10-million-transaction run completes in about twenty minutes. The adaptive router pays a small latency premium (on the order of ten percent) for its switching and probing.

Why the gap is so large. The rule-based router switched fewer than a hundred times in ten million transactions. Gradual degradation never trips its threshold until most of the damage is done, and with no exploration it never discovers that a gateway has recovered — so it sits on degraded gateways for long stretches. The adaptive router's ~1.5 million switches are not churn; they are the mechanism that keeps it on whichever gateway is healthiest right now. That also means a large share of the gap is the baseline's missing re-enable rule: a threshold router that periodically re-checks a gateway it has left would recover part of it. The multiplier is a statement about this baseline, not about threshold routing in general — which is why a fairer baseline is the first item below.

Why scale matters. At 100K transactions the rule-based router looked fine — a few hundred degradations aren't enough to expose it. The failure only becomes visible at a million transactions and beyond. A small benchmark would have shipped the wrong conclusion. The multiplier itself moves between runs (2.7× at 1M, 2.2× at 10M) because the rule-based router's outcome depends on which gateway it starts on and when the degradations land; the adaptive router's success rate stayed within a point of itself across all three scales.

What this benchmark doesn't show. Only two routers were compared. A greedy baseline, a frozen-PPO variant and an oracle that routes to the true-best gateway would separate "reacting at all" from "reacting well" and show the ceiling — that's the first thing I'd add (below).

Deployment

Shadow mode
Ran alongside production, logging the recommended gateway per transaction without executing it.
Rollout
Then live traffic, behind guardrails that roll back automatically if success rate or latency regresses against control. Success rate on the routed traffic was higher than the control.
Measurement
The benchmark above was the basis for the rollout decision; live performance is tracked against the control group on the same success-rate metric.

What I'd do differently

A fairer baseline

Give the threshold router a re-enable rule — re-check a gateway it left after a cooldown — and report absolute success rates for both. The headline multiplier should survive that; if it shrinks, the honest number is the smaller one.

Complete the ablation

Random, greedy, frozen PPO and an oracle alongside the two routers benchmarked. The interesting number is adaptive vs. oracle — what exploration costs.

Put the PPO prior to the test

Wire the trained policy into the online layer and measure whether it beats the tracker-only bandit. If it doesn't, drop it.

Use the literature's bandits

Staleness probes and drift boosts are heuristics doing the job of sliding-window or discounted UCB, or Thompson sampling with forgetting — the standard algorithms for bandits whose arms change over time. Try those as the online layer.

Route per segment

Gateways degrade per payment method or bank, not globally. A contextual bandit over gateway × segment is the obvious next model.

Replay real incidents

The simulator was built by the same person as the router. Replaying logged production incidents would be a more convincing test than a synthetic environment.

Report regret over time

Cumulative regret against the oracle shows when the router loses — at onsets or during recoveries — which is where the next improvement is.

Related work

The UCB1 algorithm (Auer, Cesa-Bianchi & Fischer, 2002) for the exploration bonus; discounted and sliding-window UCB (Garivier & Moulines, 2011) as the principled treatment of non-stationary arms this router approximates with heuristics; PPO (Schulman et al., 2017) for the pre-trained policy.

Code & artifacts

Proprietary to Razorpay. Stack: Python; Gymnasium (the standard reinforcement-learning environment interface) and Stable-Baselines3 for the PPO pre-training; an online-learning service with the observation tracker and UCB router; shadow-mode logging and guardrail alerts.
