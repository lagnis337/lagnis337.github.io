Adaptive payment-gateway router

The router finds the payment gateways that start to fail. It then moves the traffic to better gateways. It learns from the result of each transaction.

Razorpay · 2026 · Owner: framing, simulator, agent, benchmark, shadow-mode and rollout measurement; platform engineering owned production integration

This is an industry project at a payments company. The code and the data are proprietary, thus this page shows only the method. All the numbers on this page come from the synthetic benchmark.

Problem

A payments platform sends each transaction to one of several gateways. A gateway can become bad suddenly, partially, and temporarily. Static rules continue to send traffic to a bad gateway until a person sees the problem and changes the weights. This can take hours, and each hour of incorrect routing causes failed payments and a loss of revenue.

Rejected: predict

Calculate a forecast of the success rate of each gateway, then send the traffic to the best gateway. This method fails when you need it most. Gateway failures are non-stationary and are rare in the training data. When the forecast is ready, the damage is already done.

Chosen: respond

An agent monitors only the results of the transactions that it sends: success, failure, and latency. When the health of a gateway decreases, the agent immediately moves the traffic. The agent makes no forecast. It learns to adapt.

Key insight It is almost impossible to predict a gateway failure, but it is possible to react quickly. The correct model is a non-stationary multi-armed bandit. In this type of problem, each decision shows only its own result, and the best option changes with time. The router must explore sufficiently to see that a gateway is good again. It must also exploit sufficiently to prevent a loss of transactions on a bad gateway. With this model, the router does not need a forecast of the future.

Observations, actions, environment

Constraint
The router does not see the true condition of a gateway. It calculates all its knowledge from the transactions that it sent. Production has the same constraint.
Action
Choose one of N gateways for each transaction.
Observation
A small set of features for each gateway. The router calculates each feature from a moving window of the recent results of that gateway. Neutral values apply until the router has sampled the gateway a small number of times.
Reward
The signal that the agent optimises. A success gives a reward and a failure gives a penalty. The penalty is smaller than the reward, thus the agent continues to try. A high latency gives a penalty. A change to a different gateway gives a bonus when the success rate of the current gateway decreases, thus the agent moves the traffic before many failures occur.

Simulator. Each gateway has hidden parameters that the agent never sees: a base success rate, a volatility, a current health, and a degradation pattern (stable, slow decay, sudden crash, or bursty). A turbulence manager starts the degradations at random times. It decreases the success rate slowly to a very low value, keeps it there for some time, and then increases it slowly. Latency spikes occur independently. These slow changes are intentional, because a sudden crash is easy to find and a slow decrease looks like noise. The simulator is more turbulent than production, thus a router that operates here has a margin.

Production features. The service calculates the same 8 observations from moving windows of the recent results of each gateway, and then sends them to the router.

Approach

  1. Score every gateway with an upper confidence bound (UCB)

    UCB = empirical success rate + exploration bonus + staleness bonus − latency penalty. The exploration bonus is √(log N / nᵢ) from the UCB1 algorithm. It is large for a gateway with few samples and becomes small when more data is available. The staleness bonus increases the score of a gateway that the router did not use recently, thus the router tries again a gateway that is good again. A slow gateway gets a penalty.

  2. Detect drift and explore harder

    Before each decision, the router compares the success rate of the current gateway in the most recent transactions with the success rate in the group before. A large decrease shows a degradation, and the router increases the exploration rate to find a different gateway. If there is no degradation, the exploration rate decreases slowly to a small value. This value is never zero, thus the router always continues to examine the gateways.

  3. Never do the obviously wrong thing

    This is a hard limit. The router sends no traffic to a gateway if its observed success rate is less than a threshold. The check is simple and has a low cost in the benchmark. A payments team needs this type of guarantee before it can use a system that learns.

  4. Learn online, not offline

    There is no retraining step. The tracker is the model, and each transaction updates it. The behaviour of a gateway changes more quickly than an offline model can be refreshed.

  5. A PPO policy, trained but not in the loop

    Proximal Policy Optimization (PPO) is a usual deep reinforcement-learning algorithm. I trained a PPO agent with a small neural network in a Gymnasium environment on the simulator, with the reward above, as a possible start point for the online layer. The router that I tested and deployed makes its decisions only from the observation tracker. The PPO policy is not in the decision path. It stays as the next experiment (see below).

Benchmark

The benchmark compares two routers in the turbulence simulator, at three sizes. The two routers have the same constraint: they see only the results of their own transactions. The rule-based router is an example of usual threshold routing. It stays on a gateway until the observed success rate in a short window is less than a fixed threshold. It then changes to a different gateway and waits for a cooldown time. All the numbers below come from the synthetic environment and are relative to this baseline.

The run with 10 million transactions needs approximately twenty minutes. The adaptive router has a small increase of latency, approximately ten percent, because it changes gateways and sends probes.

Why the difference is large. The rule-based router changed the gateway less than one hundred times in ten million transactions. A slow degradation does not cross its threshold until most of the damage is done. The rule-based router does no exploration, thus it does not find that a gateway is good again and it stays on a bad gateway for a long time. The 1.5 million changes of the adaptive router are not a problem, because they keep the traffic on the best gateway at each moment. A large part of the difference is thus the missing re-enable rule in the baseline, and a threshold router that examines a gateway again after a cooldown time can recover a part of it. The multiplier applies to this baseline and not to all threshold routers, thus a better baseline is the first item below.

Why the size of the test is important. With 100 thousand transactions the rule-based router looked satisfactory, because a few hundred degradations are not sufficient to show the problem. The failure becomes visible at one million transactions and more, thus a small benchmark gives an incorrect conclusion. The multiplier also changes between the runs, from 2.7 times at 1 million to 2.2 times at 10 million. The cause is the rule-based router: its result depends on its first gateway and on the times of the degradations. The success rate of the adaptive router changed by less than one point between the three sizes.

What this benchmark does not show. The test compares only two routers. A random baseline, a greedy baseline, a frozen PPO agent, and an oracle that always selects the best gateway can show the difference between a reaction and a good reaction, and also the maximum that is possible. This is the first addition that I recommend (see below).

Deployment

Shadow mode
The router operated in parallel with production. It recorded the recommended gateway for each transaction, but it did not execute the decision.
Rollout
Then the router got live traffic, with guardrails that do an automatic rollback if the success rate or the latency becomes worse than the control. The success rate of the routed traffic was higher than the success rate of the control.
Measurement
The benchmark above was the basis for the decision to release. A control group measures the live performance with the same success-rate metric.

What I'd do differently

A fairer baseline

Give the threshold router a re-enable rule: it must examine a gateway again after a cooldown time. Then report the absolute success rates of the two routers. If the multiplier becomes smaller, the smaller value is the correct value.

Complete the ablation

Add a random baseline, a greedy baseline, a frozen PPO agent, and an oracle to the benchmark. The important number is the difference between the adaptive router and the oracle, because this difference is the cost of the exploration.

Put the PPO prior to the test

Put the trained policy in the online layer and measure if it is better than the bandit that uses only the tracker. If it is not better, remove it.

Use the literature's bandits

The staleness probes and the drift boosts are heuristics. Sliding-window UCB, discounted UCB, and Thompson sampling with forgetting do the same task, and they are the usual algorithms for bandits with arms that change. Use one of them in the online layer.

Route per segment

A gateway can become bad for one payment method or one bank and stay good for the others. A contextual bandit for each gateway and each segment is the next model.

Replay real incidents

The same person wrote the simulator and the router. A test with the records of true production incidents is more convincing than a synthetic environment.

Report regret over time

The cumulative regret against the oracle shows when the router loses points: at the start of a degradation, or during a recovery. This is where the next improvement is.

Related work

The exploration bonus comes from the UCB1 algorithm (Auer, Cesa-Bianchi and Fischer, 2002). Discounted UCB and sliding-window UCB (Garivier and Moulines, 2011) are the correct methods for arms that change with time, and this router does the same task with heuristics. The pre-trained policy uses PPO (Schulman et al., 2017).

Code & artifacts

The code is proprietary to Razorpay. Stack: Python, Gymnasium (the usual interface for reinforcement-learning environments), and Stable-Baselines3 for the PPO pre-training. An online-learning service contains the observation tracker and the UCB router. Shadow-mode logging and guardrail alerts complete the system.
