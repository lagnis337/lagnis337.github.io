Slack-native AI analyst

Razorpay · 2025–2026 · Solo: design, wiki, agent, guardrails, rollout

Industry project. Code and data are proprietary; this is a methods write-up using only publicly stated figures.

Problem

A 127-person product and operations team asked the same kinds of questions every day — "what was X last week for merchant Y?", "how do we define an active user?", "which dashboard has Z?" — and each one became a ticket for a small data team. The knowledge needed to answer them existed, spread across 2,000+ documents, dashboards, column comments and people's heads, but nobody could find it and no two documents agreed.

The goal was an agent in Slack that answers from the team's own definitions, shows its working, and gets more reliable as people use it — without giving a language model free rein over a production warehouse.

Framing. Not retrieval-augmented generation over a document pile. The documents were compiled once into a persistent, human-ratified wiki, and the agent navigates that wiki the way an analyst would — read the index, open the relevant pages, ask a clarifying question if the request is ambiguous, then write and run the SQL.

Data: the wiki

Built on the LLM Wiki pattern (Karpathy) and laid out like the Open Knowledge Format (Google): a git repository of markdown, one page per concept — tables, metrics, dashboards — with YAML frontmatter, 100+ pages compiled from the 2,000+ source documents.

ElementWhat it does
index.mdCatalogue of every page with a one-line summary. The agent reads it first on every query and opens only the pages it needs — index-first navigation, no embeddings. Frontmatter (type, tags, status) is what makes this navigable.
rules.md and the reading skillPage templates, frontmatter conventions, how to ingest a source, how to propose a change — and a well-defined skill that tells any model how the repository is to be read when answering a question. The skill, not the model, carries the method.
log.mdAppend-only record of every change, with date and author.
Page statusEvery page is draft until a human ratifies it; the agent answers only from active pages. Drafts exist, but they can't produce answers.
Table and metric pagesSchema, grain, join paths, caveats; metric definitions with canonical SQL. This is what "schema-grounded" means here — the model sees curated pages, not raw DDL.
PlaybooksEvery SQL that produced a ratified answer is saved parameterised — merchant, date range, segment as parameters — so a similar question reuses a known-good query instead of generating a new one.

Validation before merge. Every proposed page or change is checked against live data in the warehouse before it can be ratified — a metric page's canonical SQL has to run and return sensible numbers, not just read well.

Approach

Model. Deliberately none in particular. The Slack agent selects the model at run time, and the repository is structured so that any capable, popular model can navigate it — the reading skill and the wiki's conventions do the work that would otherwise be baked into prompts for one vendor's model. Claude frontier models were used most, but the system doesn't depend on them.

Query path. The agent is instructed to think like a data analyst rather than a search engine: if the question is ambiguous ("revenue" for which product, which date basis?) it asks one clarifying question before reading anything. Then it reads index.md, opens only the metric and table pages the question needs, checks for a matching playbook, and either fills the playbook's parameters or writes new SQL grounded on the pages' schema and join paths.

Guardrails. The bot's warehouse service account can only SELECT on the curated schema, and results are capped at 10,000 rows. It cannot see raw event tables and cannot write.

Showing its work. Every answer carries a footnote: the SQL that ran, the wiki pages traversed, and the time taken at each step — repository access, navigation, query execution. Askers can check the definition it used; I could see where the time went.

The 96% is a satisfaction rate, not an execution-accuracy figure: askers rate whether the answer looked right and was useful, and a plausible wrong answer can earn a 👍. Its value is as a trend and as the trigger for the loop below. The most common cause of a 👎 was incomplete wiki context — a metric or table the wiki didn't yet cover — which is the expected failure mode of a knowledge base designed to grow with use, and exactly what the loop fixes.

The maintenance loop. A scheduled skill runs daily: it scrapes the day's responses from Slack — the thumbs-downs in particular — works out what the wiki was missing or wrong, drafts the change (a new metric page, a corrected join path, a new playbook) and pushes it to the repository as a pending proposal. I validate it against live data and ratify or reject. The wiki gets better every day; the models come and go underneath it.

What I'd do differently

  • A real evaluation set. A fixed set of questions with human-written reference SQL and results on a frozen snapshot would give execution accuracy — a number that can't be flattered by polite thumbs-ups — and would make ablations possible (with vs. without playbooks; with vs. without clarifying questions).
  • Categorise failures. "Incomplete context" is one bucket; time-grain confusion, missing filters and wrong joins are probably hiding inside it, and each needs a different fix.
  • Compile metrics rather than generate. The metric pages already hold canonical SQL; a metric-request compiler over them would leave generation only for genuinely novel questions.
  • Query-time cost. Reading the repository per query is honest and auditable but slow at the tail; caching the index and hot pages would cut the median well below two minutes.

Related work

LLM Wiki (Karpathy) — the pattern of an LLM incrementally compiling and maintaining a persistent markdown wiki, with index.md, log.md, a schema file, and answers filed back, rather than re-retrieving from raw sources on every query. Open Knowledge Format (Google) — the layout of that wiki for data: one markdown page per dataset / table / metric with YAML frontmatter, schema tables and join paths, curated like code. This project applied both to a live warehouse and put a Slack agent, guardrails and a human-ratification loop on top.

Code & artifacts
