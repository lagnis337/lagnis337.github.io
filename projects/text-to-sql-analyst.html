Slack-native AI analyst

A Slack agent answers the data questions of a team. It uses the approved wiki of the team, writes the SQL, and shows its sources.

Razorpay · 2025–2026 · Solo: design, wiki, agent, guardrails, rollout

This is an industry project. The code and the data are proprietary, thus this page shows only the method.

Problem

A team of 127 persons in product and operations asked the same types of question every day. Examples: what was X last week for merchant Y?, what is the definition of an active user?, and which dashboard contains Z?. Each question became a ticket for a small data team. The answers existed in more than 2,000 documents, in dashboards, in column comments, and in the memory of persons. Nobody could find them, and two documents frequently gave different answers.

Before

A queue of tickets. The median wait was some days, and persons answered the same questions again and again.

Goal

An agent in Slack that answers with the own definitions of the team. It shows its sources, it becomes more reliable with use, and it never gets full access to the data warehouse.

Key insight This system is not retrieval-augmented generation (RAG), which collects parts of documents for a language model at each question. A person compiled the documents one time into a permanent wiki, and a person approves each page. The agent then navigates the wiki like an analyst. It reads the index, opens the necessary pages, asks a question if the request is ambiguous, and then writes and executes the SQL (Structured Query Language) query. Each correction makes the wiki better, and the models below it can change.

The wiki

Pattern
The loop that compiles and maintains the wiki comes from LLM Wiki (Karpathy; LLM is a large language model). The layout comes from the Open Knowledge Format (Google). The wiki is a git repository of markdown files, with one page for each table, metric, or dashboard. Each page has a small header with structured metadata (YAML frontmatter: type, tags, status).
Size
More than 100 approved pages, compiled from more than 2,000 source documents.
Grounding
A table page contains the schema, the grain, the join paths, and the cautions. A metric page contains the definition and the canonical SQL. The model reads only these curated pages and never the raw schema of the database. This is the meaning of schema-grounded on this page.
Validation
A person tests each new page and each change against live data in the warehouse before the approval. The canonical SQL must execute and must give correct numbers.
File / fieldRole
index.mdA catalogue of all the pages, with one line for each page. The agent reads this file first for each question and then opens only the necessary pages. The navigation starts at the index, and the system uses no embeddings.
rules.md + reading skillThe templates of the pages and the conventions for the metadata. The file also tells how to ingest data, how to answer, and how to propose a change. The skill tells each model how to read the repository, thus the method is in the repository and not in the model.
metrics.md → playbooksThe metrics that persons ask for frequently. Each metric has a link to an approved parameterised SQL playbook, with parameters for the merchant, the date range, and the segment. A known metric thus gets a known query, and the agent writes new SQL only for the questions that no playbook covers.
log.mdA record of each change, with the date and the author. The system only adds lines to this file.
status fieldA new page is a draft page until a person approves it. The agent answers only from active pages.

Approach

  1. Clarify before reading

    The instructions tell the agent to operate like a data analyst and not like a search engine. If a question is ambiguous, for example the word revenue without a product or a date basis, the agent asks one question before it opens a page.

  2. Navigate, don't retrieve

    The agent reads index.md. It then opens only the metric pages and the table pages that the question needs. It also examines metrics.md for a playbook. If a playbook is available, the agent puts the parameters in the playbook. If no playbook is available, the agent writes SQL with the schema and the join paths from the pages.

  3. Any model

    The Slack agent selects the model at run time. The repository and the reading skill let each sufficiently good model navigate the wiki. Claude frontier models did most of the work, but the system does not depend on them.

  4. Guardrails

    The database account of the agent can only read (SELECT) from the curated schema. The number of rows in a result has a limit. The account has no access to the raw event tables and can write nothing.

  5. Show the work

    Each answer has a footnote. The footnote gives the SQL that ran, the pages that the agent read, and the time and the token cost of each step: the access to the repository, the navigation of each page, and the execution of the query. The footnote also gives the total. The asker can examine the definition. I used the cost of each page to find the pages that were expensive to read, and then I made them smaller.

  6. Maintain daily

    A scheduled skill reads the Slack answers of the day, and especially the negative ratings. It calculates what the wiki did not contain or what was incorrect. It then writes the change, for example a metric page, a correction of a join path, or a new playbook, and sends it as a proposal. I test the proposal against live data and then approve it or refuse it.

The value of 96% is a satisfaction rate and not an execution accuracy. The askers show if the answer looked correct and was useful, thus an incorrect but plausible answer can also get a positive rating. The value is useful as a trend and as the start signal for the maintenance loop.

What I'd do differently

A real evaluation set

Make a fixed set of questions, with reference SQL and reference results on a frozen copy of the data. This set gives an execution accuracy that a polite rating cannot change. It also permits ablations: with and without the playbooks, and with and without the clarifying question.

Categorise failures

Incomplete context is only one group. Confusion about the time grain, missing filters, and incorrect joins are probably in this group, and each of them needs a different correction.

Compile metric variations

The playbooks cover the exact matches. A compiler for metric requests (metric, filters, and grain to SQL) can give the same guarantee for the variations of the known metrics.

Cache from the cost data

The footnote shows which pages the agent reads most frequently and which pages have the highest cost. A cache for the index and for these pages can decrease the median time below two minutes, and the audit trail stays complete.

Related work

LLM Wiki (Karpathy) shows a large language model that compiles and maintains a permanent markdown wiki, with index.md, log.md, a schema file, and the answers in the repository. The model thus does not read the raw sources again for each question. The Open Knowledge Format (Google) gives the layout for data: one markdown page for each data set, table, or metric, with YAML frontmatter, schema tables, and join paths, and with the same care as code. This project uses the two ideas on a live warehouse and adds a Slack agent, guardrails, and an approval loop with a person.

Code & artifacts

The code is proprietary to Razorpay. Stack: a markdown wiki in git with structured page metadata and a status field, a model-agnostic Slack agent that selects the model at run time and uses a defined reading skill, a read-only account on the data warehouse, and a daily scheduled skill that proposes changes to the wiki for the approval of a person.
