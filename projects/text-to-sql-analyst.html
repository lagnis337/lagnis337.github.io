Problem

A 127-person product and operations team asked the same kinds of questions every day — "what was X last week for merchant Y?", "how do we define an active user?", "which dashboard has Z?" — and each became a ticket for a small data team. The answers existed, spread across 2,000+ documents, dashboards, column comments and people's heads; nobody could find them, and no two documents agreed.

Before

A ticket queue. Median wait measured in days; the same questions answered again and again by hand.

Goal

An agent in Slack that answers from the team's own definitions, shows its working, gets more reliable with use — and never has free rein over the warehouse.

Key insight Not retrieval-augmented generation over a document pile. The documents were compiled once into a persistent, human-ratified wiki, and the agent navigates it the way an analyst would — read the index, open the relevant pages, ask a clarifying question if the request is ambiguous, then write and run the SQL. The wiki compounds with every correction; the models come and go underneath it.

The wiki

Pattern
LLM Wiki (Karpathy) for the compile-and-maintain loop; Open Knowledge Format (Google) for the layout — a git repo of markdown, one page per table / metric / dashboard, YAML frontmatter.
Size
100+ ratified pages compiled from 2,000+ source documents.
Grounding
Table pages carry schema, grain, join paths and caveats; metric pages carry definitions with canonical SQL. The model sees curated pages, never raw DDL — that's what "schema-grounded" means here.
Validation
Every proposed page or change is run against live warehouse data before it can be ratified. Canonical SQL has to execute and return sensible numbers, not just read well.
File / fieldRole
index.mdCatalogue of every page with a one-line summary. Read first on every query; the agent opens only the pages it needs. Index-first navigation, no embeddings.
rules.md + reading skillPage templates and frontmatter conventions; how to ingest, answer and propose. The skill tells any model how the repo is to be read — the method lives here, not in the model.
metrics.md → playbooksRegularly asked metrics, each linked to a ratified, parameterised SQL playbook (merchant, date range, segment). Known metric → known-good query; generation only for what playbooks don't cover.
log.mdAppend-only record of every change, with date and author.
status frontmatterdraft until a human ratifies; the agent answers only from active pages.

Approach

  1. Clarify before reading

    The agent is instructed to think like a data analyst, not a search engine. If a question is ambiguous ("revenue" — which product, which date basis?) it asks one clarifying question before opening anything.

  2. Navigate, don't retrieve

    Read index.md; open only the metric and table pages the question needs; check metrics.md for a matching playbook. Fill the playbook's parameters if there is one, otherwise write SQL grounded on the pages' schema and join paths.

  3. Any model

    The Slack agent selects the model at run time; the repo and the reading skill are built so any capable model can navigate them. Claude frontier models were used most, but nothing depends on them.

  4. Guardrails

    The bot's service account can only SELECT on the curated schema; results are capped at 10,000 rows; no raw event tables, no writes.

  5. Show the work

    Every answer carries a footnote: the SQL that ran, the pages traversed, and the time and token cost of each step — repo access, per-page navigation, query execution — plus the total. Askers check the definition; I used per-page costs to find pages that were expensive to read every time and restructure them.

  6. Maintain daily

    A scheduled skill scrapes the day's Slack responses — the 👎s especially — works out what the wiki was missing or wrong, drafts the change (a metric page, a corrected join path, a new playbook) and pushes it as a pending proposal. I validate against live data and ratify or reject.

96% is a satisfaction rate, not execution accuracy — askers rate whether the answer looked right and was useful, and a plausible wrong answer can earn a 👍. Its value is as a trend and as the trigger for the maintenance loop.

What I'd do differently

A real evaluation set

Fixed questions with reference SQL and results on a frozen snapshot → execution accuracy that can't be flattered by polite thumbs-ups, and ablations (with vs. without playbooks, with vs. without clarifying questions).

Categorise failures

"Incomplete context" is one bucket; time-grain confusion, missing filters and wrong joins are probably inside it, and each needs a different fix.

Compile metric variations

Playbooks already cover exact matches; a metric-request compiler (metric + filters + grain → SQL) would extend the no-generation guarantee to variations of known metrics.

Cache from the cost data

The footnote already shows which pages are read most and cost most; caching the index and hot pages cuts the median well below two minutes without losing auditability.

Related work

LLM Wiki (Karpathy) — an LLM incrementally compiling and maintaining a persistent markdown wiki, with index.md, log.md, a schema file and answers filed back, instead of re-retrieving from raw sources on every query. Open Knowledge Format (Google) — that wiki's layout for data: one markdown page per dataset / table / metric with YAML frontmatter, schema tables and join paths, curated like code. This project applied both to a live warehouse and added a Slack agent, guardrails and a human-ratification loop.
